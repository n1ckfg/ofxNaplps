# ofxNaplps Architecture

This openFrameworks addon provides a complete toolset for decoding, rendering, and encoding NAPLPS/Telidon vector graphics files. It is a C++ port of the JavaScript libraries `naplps.js` and `TelidonP5.js`.

The architecture is divided into two primary subsystems, kept strictly separated: decoding/parsing (in `Naplps.h`/`Naplps.cpp`) and rendering (in `Telidon.h`/`Telidon.cpp`).

## 1. Decoding and Parsing (`Naplps.h` / `Naplps.cpp`)

The decoder reads binary `.nap` files or byte streams and converts them into an intermediate representation composed of discrete drawing commands. It has no dependencies on openFrameworks' rendering subsystems.

### Core Classes

*   **`NapDecoder` (aliased as `Naplps`)**: The main entry point for reading `.nap` files. It manages the byte stream parsing, detecting the format version (699 Telidon or 709 NAPLPS), and accumulating a sequence of `NapCmd` objects.
*   **`NapState`**: Holds the mutable decoding state (such as the current drawing cursor, color map, and domain constraints). By encapsulating this state within the decoder (unlike the global state in the original JS), multiple files can be decoded safely without interference.
*   **`NapCmd`**: Represents a single decoded drawing instruction (e.g., SET COLOR, LINE_ABS, POLY_FILLED). It bundles the command's operation type (`NapOpcode`), associated data coordinates (`points`), and assigned color (`col`).
*   **Data Primitives**:
    *   **`NapChar`**, **`NapOpcode`**, **`NapData`**: Single-byte parsing utilities for interpreting the 7-bit ASCII/binary sequences.
    *   **`NapDataArray`**, **`NapVector`**, **`NapText`**: Multi-byte classes that decode complex coordinates (XY/XYZ) and strings according to the NAPLPS specification's variable bit-length encoding.

### Encoding

*   **`NapEncoder`**: Provides the reverse operation. It takes a vector of `NapInputWrapper` objects (representing colored strokes and fills) and generates the equivalent binary `.nap` byte stream. It supports adjustable precision (data length per coordinate) and spatial normalization.

## 2. Rendering (`Telidon.h` / `Telidon.cpp`)

The renderer consumes the intermediate `NapCmd` objects generated by the decoder and translates them into openFrameworks graphical calls (`ofPath`, `ofDrawCircle`, etc.). 

### Core Classes

*   **`TelidonDraw` (aliased as `Telidon`)**: The primary rendering interface. In an `ofApp`, this is typically updated (`update()`) and drawn (`draw()`) every frame. It supports "progressive drawing" to simulate the slow, baud-rate-limited rendering of original Telidon terminals.
*   **`TelidonDrawCmd`**: A wrapper around a single `NapCmd` that handles the specific openFrameworks draw calls required for that command. It tracks its own progressive drawing state (e.g., how many points of a polygon have been drawn so far).
*   **`TelidonRenderState`**: Manages the openFrameworks drawing state (fill color, stroke settings) that must persist *across* sequential commands. NAPLPS relies on this state carrying over (e.g., a "SET COLOR" command affects all subsequent shapes until changed).

## Data Flow

1.  **Load**: `naplps.load("file.nap")` reads the binary file.
2.  **Decode**: The `NapDecoder` parses the bytes into a `std::vector<NapCmd>`.
3.  **Setup Renderer**: `telidon.setup(naplps, width, height)` prepares the renderer with the decoded commands.
4.  **Update/Draw**: During the application's run loop, `telidon.update()` advances the progressive drawing timer, and `telidon.draw()` renders the currently visible elements to the openFrameworks window.
